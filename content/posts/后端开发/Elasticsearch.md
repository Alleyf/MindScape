# 1 🚀 Elasticsearch 面试指南：从入门到精通

## 1.1 第一阶段：基础概念与架构 (必问)

这部分主要考察你对 ES 基本定位和核心组件的理解。

### 1.1.1 ES 是什么？为什么选择它？

*   **定义**：基于 Lucene 的分布式搜索和分析引擎。
*   **核心优势**：
    *   **近实时搜索** (Near Real-Time, NRT)：写入后约 1 秒可搜。
    *   **分布式**：自动分片、副本，横向扩展能力强。
    *   **多租户**：支持多个索引。
    *   **丰富的查询语言** (DSL)。
    *   **Schema Free** (动态映射)，但也支持严格模式。

### 1.1.2 核心概念类比 (关系型数据库 Vs ES)

| 关系型数据库 (RDBMS) | Elasticsearch |
| :--- | :--- |
| Database (数据库) | Index (索引) |
| Table (表) | Type (7.x 已废弃，现为 Index) / Mapping |
| Row (行) | Document (文档) |
| Column (列) | Field (字段) |
| Schema (模式) | Mapping (映射) |
| SQL | DSL (Domain Specific Language) |
| `select * from t where id=1` | `GET /index/_doc/id` |

### 1.1.3 倒排索引 (Inverted Index) —— **核心中的核心**

*   **问题**：为什么 ES 搜索这么快？
*   **回答要点**：
    *   传统数据库是**正排索引**（文档 ID -> 内容），适合根据 ID 查内容，不适合全文检索。
    *   ES 使用**倒排索引**（词项 Term -> 文档 ID 列表）。
    *   **结构**：
        *   **Term Dictionary (词典)**：有序存储所有词项，支持二分查找。
        *   **Term Index (词典索引)**：词典的缓存（如 FST 数据结构），占用内存小，快速定位词典位置。
        *   **Posting List (倒排表)**：记录包含该词项的文档 ID 列表、频率、位置等信息。
    *   **优化**：使用 Frame of Reference (FOR) 压缩算法和 Roaring Bitmaps 压缩倒排表，极大节省空间并加速交集/并集运算。

### 1.1.4 集群架构组件

*   **Node (节点)**：集群中的一台服务器。
*   **Cluster (集群)**：一组节点的集合，共享同一个 `cluster.name`。
*   **Index (索引)**：具有相似特征的文档集合。
*   **Shard (分片)**：
    *   **Primary Shard (主分片)**：存储原始数据，数量在创建索引时确定，**后期不可修改**（除非重索引）。
    *   **Replica Shard (副本分片)**：主分片的拷贝，提供高可用性和读性能扩展，数量可随时调整。
*   **Document**：ES 中最小数据单元，JSON 格式。

## 1.2 第二阶段：写入与读取流程 (高频难点)

面试官常通过画图或口述流程来考察你对分布式一致性的理解。

### 1.2.1 写入流程 (Write Path)

**口诀：协调节点 -> 主分片 -> 并行副本 -> 响应**
1.  客户端发送请求给任意节点（**Coordinating Node**）。
2.  协调节点根据路由规则 (`hash(routing) % num_primary_shards`) 确定文档属于哪个主分片，转发请求。
3.  **主分片节点**执行写入操作：
    *   写入 **Translog** (预写日志，保证数据安全)。
    *   写入 **Memory Buffer** (内存缓冲)。
4.  主分片并行将请求转发给所有**副本分片节点**。
5.  副本分片执行相同操作（写 Translog + Buffer），成功后返回给主分片。
6.  主分片收到所有副本成功后，向协调节点返回成功。
7.  协调节点向客户端返回成功。
8.  **异步刷新 (Refresh)**：默认每 1 秒，将 Memory Buffer 中的数据生成新的 **Segment** 并清空 Buffer，此时数据才可被搜索（NRT 原理）。
9.  **持久化 (Flush)**：默认每 30 分钟或 Translog 满时，将 Segment 强制刷盘，并清空 Translog。

### 1.2.2 读取流程 (Read Path)

**模式：Query Then Fetch**
1.  **Query 阶段**：
    *   协调节点将请求广播到所有相关分片（主分片或副本分片，由负载均衡决定）。
    *   各分片在本地执行查询，生成一个**优先队列**（只包含文档 ID 和排序值），返回给协调节点。
    *   协调节点合并所有结果，全局排序，截取顶层结果（如 `from` 到 `size`）。
2.  **Fetch 阶段**：
    *   协调节点根据确定的文档 ID，向对应的分片发起获取完整文档内容的请求。
    *   分片返回完整文档。
    *   协调节点组装最终结果返回客户端。

> **追问**：深度分页（Deep Pagination）有什么问题？如何解决？
> *   **问题**：`from + size` 过大时，每个分片都要返回大量数据给协调节点进行全局排序，导致内存溢出 (OOM) 和网络带宽压力。
> *   **解决**：
>     *   禁止深度分页（限制 `max_result_window`）。
>     *   使用 `search_after` 参数（推荐，基于游标）。
>     *   使用 `scroll` API（适用于离线大数据量导出，非实时场景）。

## 1.3 第三阶段：进阶原理与调优 (区分度关键)

### 1.3.1 分片策略 (Sharding Strategy)

*   **分片数怎么定？**
    *   单个分片大小建议在 **30GB - 50GB** 之间。
    *   分片过多会导致集群元数据负担重，恢复慢；分片过少不利于横向扩展。
    *   公式参考：`分片数 = 总数据量 / 目标单分片大小`。
*   **路由机制**：默认 `hash(id) % 主分片数`。自定义 Routing 可以将相关数据（如同一用户订单）落在同一分片，提高查询效率。

### 1.3.2 脑裂问题 (Split-Brain)

*   **现象**：网络抖动导致集群分裂成两个独立的小集群，都选举出了 Master，导致数据不一致。
*   **解决**：设置 `discovery.zen.minimum_master_nodes` (ES 7.x 前) 或投票机制 (ES 7.x+ 自动处理)。
    *   原则：`(主节点候选数 / 2) + 1`。例如 3 个主节点候选，设置为 2。

### 1.3.3 性能优化 (Optimization)

*   **写入优化**：
    *   使用 **Bulk** 批量写入。
    *   增加 `refresh_interval` (如改为 30s)，减少 Segment 生成频率。
    *   关闭副本（初始导入时），导入完成后再开启。
    *   使用自动生成 ID (避免检查 ID 是否存在)。
    *   增加机器内存，使用 SSD。
*   **查询优化**：
    *   尽量使用 **Filter** 上下文（有缓存，不计算评分），而非 Query 上下文。
    *   控制返回字段 (`_source` filtering)。
    *   合理使用 `keyword` (精确匹配) 和 `text` (分词匹配)。
    *   利用 **Route** 减少扫描分片数量。
    *   冷热数据分离架构 (Hot-Warm-Cold Architecture)。

### 1.3.4 数据一致性

*   ES 默认是 **最终一致性**。
*   写入时可以指定 `wait_for_active_shards` 参数来控制写入成功的副本数，从而在可用性和一致性之间做权衡。

## 1.4 第四阶段：实战场景与解决方案 (加分项)

面试官可能会给出一个具体业务场景，让你设计方案。

### 1.4.1 场景 1：海量日志分析 (ELK Stack)

*   **挑战**：写入量巨大，查询多为最近几天的数据。
*   **方案**：
    *   **索引生命周期管理 (ILM)**：按天创建索引 (log-2023.10.01)，设置保留策略（如保留 30 天，过期删除）。
    *   **冷热分离**：热数据放在高性能 SSD 节点，冷数据迁移到大容量 HDD 节点或冻结 (Freeze)。
    *   **模板 (Index Template)**：预先定义 Mapping 和 Settings。

### 1.4.2 场景 2：电商商品搜索

*   **挑战**：复杂的筛选（价格、品牌、属性）、排序（销量、相关性）、拼写纠错、高亮显示。
*   **方案**：
    *   **Mapping 设计**：商品标题用 `text` (配合 ik 分词器)，品牌/分类用 `keyword`。
    *   **聚合 (Aggregation)**：实现 facets 筛选功能（如“三星”有多少个商品）。
    *   **自定义评分**：使用 `function_score` 结合销量、上架时间调整相关性得分。
    *   **同义词库**：配置 synonym filter 处理“手机”=“移动电话”。

### 1.4.3 场景 3：数据同步 (MySQL -> ES)

*   **方案**：
    *   **CANAL / Debezium**：监听 MySQL Binlog，实时同步到 MQ (Kafka/RocketMQ)，再消费写入 ES（解耦、削峰）。
    *   **Logstash / Filebeat**：适合日志或定时全量同步。
    *   **双写方案**：代码层同时写 DB 和 ES（需处理一致性问题，通常加重试机制或补偿任务）。
