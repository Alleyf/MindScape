# 1 🚀 Dubbo 面试全攻略 (0 -> 1)

## 1.1 第一阶段：基础概念与架构 (必问必会)

*目标：清晰阐述 Dubbo 是什么，解决了什么问题，以及整体架构。*

### 1.1.1 什么是 Dubbo？它解决了什么问题？

*   **定义**：Apache Dubbo 是一款高性能、轻量级的开源 Java **RPC (Remote Procedure Call)** 框架。
*   **核心目标**：提供透明化的远程方法调用，完成服务治理（软负载均衡、容错、路由等）。
*   **解决痛点**：
    *   传统单体应用无法应对高并发和海量数据。
    *   手动编写 Socket/HTTP 代码耦合度高、难以维护。
    *   服务调用关系复杂，缺乏监控和治理手段。

### 1.1.2 Dubbo 的核心架构角色 (必背)

面试时最好能画出或口述这五个角色：
1.  **Provider (服务提供者)**：暴露服务的服务方。
2.  **Consumer (服务消费者)**：调用远程服务的服务方。
3.  **Registry (注册中心)**：服务注册与发现的中心（如 Nacos, Zookeeper, Consul）。**解耦**的关键。
4.  **Monitor (监控中心)**：统计服务的调用次数和调用时间（通常指 Dubbo Admin 或 SkyWalking/Pinpoint 等链路追踪）。
5.  **Container (容器)**：服务运行容器（如 Spring Boot, Tomcat, Jetty）。

### 1.1.3 调用流程 (核心逻辑)

1.  **启动**：Provider 启动后向 Registry 注册；Consumer 启动后向 Registry 订阅。
2.  **发现**：Registry 返回 Provider 地址列表给 Consumer（长连接推送变化）。
3.  **负载均衡**：Consumer 基于算法从列表中选择一个 Provider。
4.  **调用**：Consumer 通过 Proxy 发起远程调用，经过 Filter 链、序列化、网络传输。
5.  **响应**：Provider 接收请求，反序列化，执行业务逻辑，返回结果。

## 1.2 第二阶段：核心原理 (进阶核心)

*目标：展示你对底层机制的理解，这是区分初级和中高级开发者的关键。*

### 1.2.1 序列化协议 (Serialization)

*   **作用**：将对象转换为字节流进行网络传输。
*   **常见协议对比**：
    *   **Hessian2** (Dubbo 默认)：成熟稳定，但性能一般，包体积较大。
    *   **Protobuf**：Google 出品，性能极高，体积小，但需要定义 `.proto` 文件，兼容性略差。
    *   **Kryo / FST**：高性能 Java 序列化，速度快，但安全性需注意（需配置白名单）。
    *   **JSON**：可读性好，跨语言，但性能和体积较差，通常用于对外接口。
*   **面试考点**：如何选择？内部高性能选 Protobuf/Kryo，对外兼容选 JSON/Hessian。

### 1.2.2 通信框架 (Transporter)

*   **Netty**：Dubbo 默认使用 **Netty (NIO)** 作为底层通信框架。
*   **为什么选 Netty？** 高并发、异步非阻塞、零拷贝、内存管理优秀。
*   **线程模型**：
    *   **IO 线程** (Netty Boss/Worker)：只负责读写数据，不执行业务逻辑。
    *   **业务线程池** (Dubbo Thread Pool)：IO 线程将数据解码后，丢入业务线程池执行具体方法，避免阻塞 IO 线程。

### 1.2.3 负载均衡策略 (Load Balance) - 高频

Consumer 端从多个 Provider 中选一个，默认有四种策略：
1.  **Random (随机)**：**默认策略**。按权重设置随机概率。适合机器性能不均的场景。
2.  **RoundRobin (轮询)**：平滑加权轮询。适合机器性能均一，但要注意慢请求积累问题。
3.  **LeastActive (最少活跃调用数)**：优先调用活跃数（正在处理的请求数）少的机器。自动照顾慢机器，防止雪崩。
4.  **ConsistentHash (一致性哈希)**：相同参数的请求总是发到同一台机器。适合有状态服务（如缓存），但需注意节点变动时的数据迁移。

### 1.2.4 容错机制 (Cluster/Fault Tolerance) - 高频

当调用失败时，如何处理？
1.  **Failover (失败自动切换)**：**默认策略**。重试其他服务器。适合**读操作**（幂等）。*注意：配置 `retries` 参数，默认重试 2 次（共调用 3 次）。*
2.  **Failfast (快速失败)**：只发一次，失败立即报错。适合**写操作**（非幂等，如转账）。
3.  **Failsafe (失败安全)**：失败直接忽略，记录日志。适合**审计、日志记录**等非核心业务。
4.  **Failback (失败自动恢复)**：后台定时重发失败请求。适合**消息通知**。
5.  **Forking (并行调用)**：并行调用多个服务器，只要一个成功即返回。适合实时性要求极高但资源消耗大的场景（不常用）。

### 1.2.5 SPI 机制 (扩展点)

*   **什么是 SPI**：Service Provider Interface，Java 的一种服务发现机制。
*   **Dubbo 的 SPI**：Dubbo 大量使用自适应 SPI (`@Adaptive`) 和 激活扩展 (`@Activate`)。
*   **考点**：Dubbo 几乎所有组件（协议、序列化、负载均衡、过滤器）都可以通过 SPI 扩展，这是其生态丰富的原因。

## 1.3 第三阶段：高级特性与服务治理

*目标：展示你在复杂场景下的掌控能力。*

### 1.3.1 注册中心选型

*   **Zookeeper**：经典选择，基于 CP 模型（强一致性）。宕机可能导致不可用，但数据不丢失。
*   **Nacos**：阿里开源，目前主流。支持 AP (高可用) 和 CP 切换，功能更丰富（配置中心 + 注册中心），界面友好。
*   **Redis / Multicast**：较少用于生产核心环境。
*   **对比**：面试中建议回答“目前新项目首选 Nacos，老项目维持 ZK”。

### 1.3.2 动态代理

*   Dubbo 在 Consumer 端生成 Proxy，在 Provider 端生成 Skeleton (Wrapper)。
*   **方式**：默认使用 **Javassist** (字节码生成，无需依赖)，也支持 JDK 动态代理、CGLIB。
*   **优势**：透明化调用，用户感觉像调用本地方法一样。

### 1.3.3 泛化调用 (Generic Service)

*   **场景**：网关层、测试平台、没有 API 接口的客户端。
*   **原理**：不需要引用具体的 API 接口 jar 包，通过 `GenericService` 接口，传入方法名、参数类型、参数值进行调用。

### 1.3.4 优雅停机 (Graceful Shutdown)

*   **问题**：服务重启时，正在处理的请求被强行中断，导致数据不一致或客户端报错。
*   **Dubbo 方案**：
    1.  停止接收新请求。
    2.  等待已接收的请求处理完成（设置超时时间）。
    3.  关闭连接，注销注册中心。
*   **配置**：`dubbo.protocol.shutdown.wait=20000` (毫秒)。

### 1.3.5 线程模型优化

*   **Dispatcher 策略**：
    *   `all` (默认)：所有消息都派发到线程池。
    *   `direct`：所有消息直接在 IO 线程执行（慎用，易阻塞）。
    *   `message` / `connection` / `execution`：针对不同消息类型的派发策略。

## 1.4 第四阶段：生产实战与避坑 (区分度关键)

*目标：展示你有实际填坑经验，不仅仅是背书。*

### 1.4.1 如何解决服务雪崩？

*   **超时控制**：合理设置 `timeout`（方法级 > 接口级 > 全局）。
*   **重试机制**：非幂等接口严禁开启重试 (`retries=0`)。
*   **熔断降级**：集成 Sentinel 或 Hystrix。当错误率/响应时间超过阈值，快速失败，返回兜底数据，保护下游。
*   **限流**：限制接口的 QPS，防止突发流量打垮服务。

### 1.4.2 版本管理与灰度发布

*   **Version 属性**：`@DubboService(version = "1.0.0")`。
*   **场景**：
    *   不兼容升级：修改接口签名，升级 version，新旧共存。
    *   灰度发布：利用 **路由规则 (Router)** 或 **标签路由**，将特定用户（如内部员工、特定地区）的流量导向新版本服务。

### 1.4.3 多注册中心与多协议

*   **多注册中心**：同时注册到 ZK 和 Nacos，用于迁移过渡。
*   **多协议**：内部高性能用 `dubbo` 协议 (TCP)，对外暴露用 `rest` 或 `http` 协议。

### 1.4.4 常见故障排查

*   **连接超时 (Timeout)**：检查网络、GC 停顿、数据库慢查询、线程池是否满。
*   **序列化异常**：类版本不一致，缺少无参构造函数，字段类型不匹配。
*   **注册中心挂掉**：Consumer 本地有缓存，短时间内不影响调用，但无法感知新上线/下线的 Provider。

## 1.5 第五阶段：高频面试题清单 (模拟演练)

### 1.5.1 基础题

1.  **Dubbo 支持哪些协议？默认是什么？** (dubbo, http, rest, rmi… 默认 dubbo 协议，单一长连接，NIO 异步通信)。
2.  **注册中心挂了，消费者还能调用吗？** (能，因为本地有缓存地址列表，但无法感知服务变更)。
3.  **Dubbo 的默认超时时间是多少？如何配置？** (默认 1000ms，可在 `@Reference` 或配置文件中调整)。

### 1.5.2 原理题

4.  **详细描述一次 Dubbo 远程调用的全过程。** (从代理 -> 负载均衡 -> 集群容错 -> 协议层 -> 序列化 -> 网络传输 -> 服务端反向过程)。
5.  **Dubbo 的 SPI 机制和 Java 原生 SPI 有什么区别？** (Dubbo 支持按需加载、自适应扩展、激活扩展，性能更好，更灵活)。
6.  **一致性哈希负载均衡的原理是什么？解决了什么问题？** (解决参数路由问题，相同参数固定打到同一台机器，减少缓存失效)。

### 1.5.3 场景/优化题

7.  **线上出现大量超时，你如何排查？**
    *   *思路*：看监控 (RT, QPS, 错误率) -> 查日志 (是否有 Full GC, DB 慢) -> 查链路追踪 (定位是哪个环节慢) -> 检查线程池状态 -> 临时扩容或降级。
8.  **如何设计一个幂等接口？在 Dubbo 中如何保证？**
    *   *思路*：业务层唯一键 (订单号) + 数据库唯一索引 / Redis Token 机制。Dubbo 层面设置 `retries=0` 防止重复提交。
9.  **Dubbo 2.x 和 3.x 有什么主要区别？**
    *   *关键点*：3.0 支持 **应用级服务发现** (大幅降低注册中心压力，适合大规模微服务)，协议升级 (Triple 协议基于 HTTP/2，云原生友好)，接口级向应用级迁移。

## 1.6 💡 备考建议

1.  **版本意识**：现在面试尽量往 **Dubbo 3.x** 靠拢，特别是“应用级服务发现”和“Triple 协议”，这是加分项。
2.  **结合生态**：不要孤立谈 Dubbo，要结合 **Spring Cloud Alibaba** (Nacos, Sentinel) 一起讲，说明它们在微服务架构中的位置。
3.  **动手实验**：
    *   尝试配置不同的负载均衡策略看效果。
    *   模拟 Provider 宕机，观察 Consumer 的容错行为。
    *   使用 Arthas 或 SkyWalking 追踪一次调用链。
4.  **准备案例**：准备一个“通过调整线程池参数/超时时间/序列化协议”解决线上性能问题的真实（或模拟）案例。
